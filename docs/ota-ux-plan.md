# 小安话机 · 检查更新 / 升级交互方案

> 配套 `ota-remote-upgrade.md`（底层：双槽分区、下载、回滚）。本文只讲**用户怎么用**：
> 屏幕上的检查更新、语音问"有没有新版本"、更新过程中屏幕显示什么、哪些功能要关。

---

## 0. 前提（一句话）

设备必须先按 `ota-remote-upgrade.md` 第 4 节改成双槽分区并 USB 刷一次。本文所有交互都建立在这之上。

---

## 1. 三个入口，一套流程

```
入口 A  设置页「检查更新 v1.0.0 ›」  ─┐
入口 B  语音「有没有新版本」           ─┼─▶  检查  ─▶  弹窗/语音确认  ─▶  升级页  ─▶  重启  ─▶  开机提示"已升级到 v1.1.0"
入口 C  网页「固件升级」卡片           ─┘
```

三个入口共用同一个 OTA 状态机，谁触发都一样；差别只在"确认"这一步的形式（点按钮 / 说"更新" / 网页按钮）。

---

## 2. 入口 A：设置页

### 2.1 新增一行

在「设备信息」和「重新配网」之间插一行（y=296，与现有 `list_row` 同样式）：

```
 ⟳  检查更新                        v1.0.0  ›
    点击查看是否有新版本
```

- 右侧常显**当前版本号**，不用进设备信息页也能看到。
- 若后台自动检查已发现新版本：行右侧版本号旁加一个小红点，副标题改为「发现新版本 v1.1.0」。

### 2.2 点击后的三种结果

| 结果 | 屏幕表现 | 停留 |
|------|----------|------|
| 正在检查 | 该行副标题变「正在检查…」，右侧转圈 | ≤ 8 s |
| 已是最新 | 顶部 toast「已是最新版本 v1.0.0」 | 2 s |
| 检查失败 | toast「检查失败：无法连接服务器」/「网络未连接」 | 3 s |
| 有新版本 | 弹出**更新弹窗**（2.3） | 等待操作 |

### 2.3 更新弹窗（圆屏自绘，非 lv_msgbox）

直径约 300 px 的圆形深色面板，盖在设置页上方：

```
        ⟳  发现新版本
           v1.0.0  →  v1.1.0

     ┌──────────────────────┐
     │ • 新增查询时间功能      │   ← 版本说明，可上下滚动
     │ • 联网搜索可在网页关闭   │      （来自 firmware.json 的 notes）
     │ • 修复工具调用偶发报错   │
     └──────────────────────┘
       约 2.4 MB · 需 1–2 分钟

      [  稍后  ]      [ 立即更新 ]
```

- 「稍后」关闭弹窗，24 小时内不再自动弹（手动点仍可查）。
- 「立即更新」→ 前置条件检查（第 5 节）→ 通过则进入升级页；不通过则 toast 说明原因（如「通话中无法升级」）。
- 弹窗期间仍可被来电打断（来电优先）。

## 3. 入口 B：语音

### 3.1 新增两个工具

| 工具 | 作用 | 返回 |
|------|------|------|
| `check_update` | 查服务器有没有新版本 | `{current, latest, has_update, notes, size_mb}` 或 `{error}` |
| `start_update` | 开始升级 | `{ok:true}` 或 `{ok:false, reason}` |

拆成两个而不是一个带参数的，是为了让模型**必须先问再做**，不会一句"有新版本吗"就直接给人升了。

### 3.2 提示词规则（加到 `buildInstructions`）

> 客人问有没有新版本 / 能不能升级 / 固件更新 时，先调 `check_update`。
> 没有新版本：告诉客人"已经是最新版本 vX"。
> 有新版本：用一两句话说明版本号和主要更新内容，然后**问客人要不要现在更新**，并提醒"更新大约一两分钟，期间不能使用"。
> 只有客人明确同意（"更新吧""好的""现在更新"）才调 `start_update`。
> `start_update` 成功后说一句"开始更新了，请不要断电，完成后我会自动重启"，然后停止说话。

### 3.3 对话示例

```
客人：你好小安，有没有新版本？
小安：（check_update）有的，现在是 1.0.0，最新是 1.1.0，新增了查时间功能，
      还修了几个小问题。更新大概要一两分钟，期间不能用，要现在更新吗？
客人：更新吧。
小安：（start_update）好的，开始更新了，请不要断电，完成后我会自动重启。
      ── 会话结束，屏幕切到升级页 ──
```

`start_update` 内部：先让模型把那句话说完（复用 `call_front_desk` 的"等播放结束再动作"机制），再关会话、进升级页。

## 4. 入口 C：网页

「固件升级」卡片：当前版本、服务器地址、[检查更新] → 显示新版本号与说明 → [立即升级]；升级中轮询 `/ota/status` 显示进度条；另有 [从文件上传]。与屏幕共用状态机，网页发起的升级屏幕同样显示升级页。

---

## 5. 开始升级前的检查（任一不满足即拒绝，并给出原因）

| 条件 | 不满足时提示 |
|------|--------------|
| 不在 SIP 通话中 | 「通话中无法升级，请挂断后再试」 |
| Wi-Fi 已连接 | 「网络未连接」 |
| RSSI ≥ -75 dBm | 「Wi-Fi 信号较弱，请靠近路由器后再试」（手动入口可点「仍然更新」强制） |
| 内部空闲堆 ≥ 80 KB | 「设备繁忙，请稍后再试」（语音会话关闭后通常满足） |
| 电量/供电 | 本机常插电，不检查 |

---

## 6. 升级过程：关什么、显示什么

### 6.1 进入升级页时依次关闭

1. 语音会话（`VoiceSession::end()`），表情/字幕清空
2. 唤醒词检测（`WakeWord::setListening(false)`），**音频任务整体暂停**（停 I2S 读写，释放 CPU 和内部 RAM）
3. SIP 心跳与来电（升级中来电直接 486 Busy）
4. 触摸输入（升级页不响应任何触摸；BOOT 键也屏蔽）
5. 自动熄屏（保持屏幕常亮，亮度拉到 60% 以上保证可见）
6. 网页其余端点只读，只保留 `/ota/status`

保留：Wi-Fi、WebServer（供网页看进度）、串口日志。

### 6.2 升级页（全屏，圆屏自绘）

圆形进度环天然适合这块屏：

```
            ╭───────────────╮
         ╭──┤   正在升级    ├──╮
        │   │    v1.1.0     │   │     ← 外圈：进度环（0→100%，渐变色）
        │   │               │   │
        │   │     62%       │   │     ← 中央大号百分比
        │   │  1.5 / 2.4 MB │   │     ← 已下载 / 总大小
        │   │  约 40 秒      │   │     ← 预计剩余（按最近 5 s 速度估算）
         ╰──┤  请勿断电     ├──╯
            ╰───────────────╯
```

### 6.3 阶段与文案

| 阶段 | 环 | 中央 | 底部 |
|------|----|------|------|
| 准备 | 空环缓慢呼吸 | 「准备中…」 | 请勿断电 |
| 连接服务器 | 同上 | 「正在连接服务器」 | 请勿断电 |
| 下载 | 实时百分比 | 百分比 + 已下载/总量 + 预计剩余 | 请勿断电 |
| 校验 | 满环，颜色变为校验色 | 「正在校验…」 | 请勿断电 |
| 写入完成 | 满环变绿 + ✓ | 「升级完成」 | 「3 秒后重启」倒计时 |
| 失败 | 环变红 + ✕ | 「升级失败」+ 原因一行（网络中断 / 校验失败 / 空间不足） | 「10 秒后返回」或点击返回 |

下载百分比来自 `HTTPUpdate` 的进度回调（已接收字节 / Content-Length），每 250 ms 刷新一次屏幕，避免刷屏抢 CPU。

### 6.4 失败处理

- 任何失败：旧固件完好（新包写在备用槽），恢复音频/唤醒/触摸，回到设置页，toast 原因。
- 自动检查触发的失败：静默记录，下次再试，不打扰。
- 失败原因写入 NVS（最近一次），网页和设备信息页可查。

### 6.5 重启后

- 新固件首次启动：`ota_begin()` 检测到 `PENDING_VERIFY`，等 Wi-Fi + 音频 + 网页就绪后 `mark_valid`。
- 开机表情页 toast：「已升级到 v1.1.0」（3 s）。
- 若新固件 30 s 内没完成 mark_valid（崩溃/卡死），bootloader 自动回滚，旧版开机后 toast：「升级未成功，已恢复 v1.0.0」。

---

## 7. 后台自动检查

- 每天 04:00（可配）且设备处于**休眠态**时检查一次。
- 发现新版本：**不自动升级**（默认），而是在设置页那一行打红点 + 下次唤醒时小安开场白后补一句"对了，设备有新版本，需要时可以让我更新"。
- 网页可切换为「发现新版本自动升级」（适合无人值守批量部署），自动升级同样只在休眠态、凌晨执行。

## 9. 边界情况

| 情况 | 处理 |
|------|------|
| 检查时服务器返回的版本 ≤ 当前 | 视为最新；网页强制升级可指定任意版本（用于回退） |
| 弹窗开着来电 | 弹窗关闭，走来电流程；接完不自动再弹 |
| 下载中 Wi-Fi 断 | 等 15 s 重连，仍断则失败回退 |
| 下载中用户长按 BOOT | 不响应（避免误操作中断写入） |
| 语音确认时客人说"算了" | 模型不调 `start_update`，正常继续对话 |
| 模型未经确认直接调 `start_update` | 固件侧二次保护：`start_update` 仅在最近 60 s 内 `check_update` 返回过 has_update 时才生效，否则返回 `{ok:false, reason:"need_check_first"}` |
| 升级页卡住（下载 5 分钟无进展） | 看门狗超时 → 失败 → 回退 |

## 11. 插电检测：只在外接电源时允许升级

### 11.1 硬件现状（V2 原理图核对结论）

| 信号 | 去向 | 能否被 MCU 读到 |
|------|------|-----------------|
| `USB_5V`（Type-C 输入） | 只进充电芯片 ETA6098 的 VIN，并引到 J7 排针第 1 脚 | **否**，没有接任何 GPIO/EXIO |
| ETA6098 `STAT`（充电状态，开漏，充电中=低） | 只点亮板上绿色 LED | **否** |
| `BAT`（电池端） | 200K/100K 分压 → `BAT_ADC`（GPIO8） | **是**，现有 `battery_volts()` 即此 |
| 空闲 IO | GPIO0/1/3/6/7/9/12/13、EXIO5–8（TCA9554）均在 J7 排针上 | 可作为检测输入 |

结论：**出厂硬件没有"是否插电"的数字信号**，只能读到电池电压。

### 11.2 两种做法

**A. 硬件一根跳线（确定可靠，推荐量产前定）**

J7 排针上 `USB_5V`（1 脚）经 100K/100K 分压接到 `EXIO5`（28 脚）或 `GPIO3`（15 脚）：
有 5V 时读高，拔线读低，与电池满不满无关。TCA9554 输入自带约 100K 上拉，接 GPIO 则软件开内部下拉。
每台一颗电阻两根线；若 Waveshare 能定制，就是改一处走线。
固件：`power_external()` 读该脚，升级前置条件直接用它。

**B. 纯软件推断（不改硬件，启发式）**

利用 ETA6098 的行为：插电瞬间它向电池注入电流，`BAT` 电压在 1–2 s 内**跳升 50–150 mV**；拔线则**跳落**；
插电状态下电压持续 ≥ 4.10 V 且不下降；纯电池供电时电压单调缓慢下降。

判定规则（每 5 s 采样，8 次均值 + 中值滤波）：
1. 检测到 ≥ 40 mV 的上跳 → 置 `external=true`；≥ 40 mV 下跌 → `external=false`
2. 无跳变时：电压 ≥ 4.10 V 且最近 15 min 无下降趋势 → `external=true`；否则 `false`
3. 开机即插电且电池已满时只能靠规则 2，需 15 min 才能确认

已知盲区：电池刚充满后拔线，前 10–20 min 电压仍 ≥ 4.1 V 且下降极慢，可能误判为插电。

### 11.3 建议的升级门槛（两种做法通用）

```
允许升级 = external_power
         || (battery_pct >= 60 && 用户在弹窗/网页点了「仍然升级」)
拒绝文案 = 「请连接电源后再升级」
```

- 双槽 + 回滚意味着升级中断电**不会变砖**，插电检查是为了体验（避免升一半重启回旧版让客人困惑），不是安全底线。
  因此软件推断的少量误判可以接受，并用 60% 电量兜底。
- 语音入口：`check_update` 返回里带 `external_power` 字段；未插电时小安直接说
  「设备现在没有接电源，请插上电源后再让我更新」，不进入确认流程。
- 弹窗与网页：未插电时「立即更新」置灰，显示「请连接电源」；电量 ≥ 60% 时额外给「仍然更新」小字按钮。

### 11.4 建议

原型/你手上这台：先用 B（软件推断）把整条 OTA 流程跑通。
批量部署前：接 A 的跳线（或请 Waveshare 改板），把 `power_external()` 切到硬件信号，B 作为无硬件信号时的回退。
